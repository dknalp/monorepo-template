## Agent Team

This project uses the **team-lead agent system**. Every prompt in this project
is handled by the team-lead agent, which coordinates specialized workers.

### How it works

- **Team Lead** receives every task, analyzes it, and decides which workers to use
- **Workers** do the actual implementation (frontend, backend, tests, review, etc.)
- **Team Lead never writes code directly** — all implementation goes through workers
- For simple conversational questions, Team Lead can answer directly without spawning workers

### Mandatory behavior

- Complex or multi-step tasks → Team Lead MUST use workers (worker-frontend, worker-backend,
  worker-tester, worker-reviewer, worker-devops, worker-researcher, worker-architect, worker-security)
- Team Lead MUST NOT implement features directly — spawn the appropriate worker
- Every worker brief must include project-context from this file

## Project Stack

- **Language/Runtime:** TypeScript (Node 20+) + Go 1.22
- **Frontend Framework:** Next.js 15 + React 19
- **Styling:** Tailwind CSS 4 (shared preset in `packages/ui/tailwind-preset.ts`)
- **Backend:** Go 1.22, stdlib `net/http` (no framework)
- **Database:** PostgreSQL — one DB per service (database-per-service pattern)
- **Monorepo (JS):** Turborepo 2 + pnpm 9 workspaces
- **Monorepo (Go):** native `go.work` (Go workspaces)
- **Test runner:** `go test ./...` (Go) / add Vitest for TS
- **CI:** GitHub Actions (`.github/workflows/ci.yml`)
- **Services (Docker):** api, auth, storage, web, db-api, db-auth, db-storage

## Project Structure

```
apps/
  web/          Next.js main app (port 3000)
  admin/        Next.js admin app (port 3001)
services/
  api/          Go API gateway (port 8080) — cmd/api/main.go entry point
  auth/         Go auth service (port 8081) — cmd/auth/main.go entry point
  storage/      Go storage service (port 8082) — cmd/storage/main.go entry point
packages/
  go-api-lib/   Shared Go: middleware, response helpers, errors
  ui/           Shared React components + Tailwind preset
infra/
  docker-compose.yml
  dockerfiles/  One Dockerfile per service
```

- Entry points: `services/<name>/cmd/<name>/main.go`
- Business logic: `services/<name>/internal/{handler,service,repository}/`
- Shared Go: `packages/go-api-lib/`
- Shared UI: `packages/ui/components/`
- Config files: `turbo.json`, `pnpm-workspace.yaml`, `go.work`

---

## The 5 Non-Negotiable Rules

1. **`cmd/<service>/main.go` is bootstrap only** — wire deps, start server, nothing else
2. **Database-per-service** — services never share a DB schema
3. **Cross-service calls go through HTTP interfaces only** — never shared memory or DB
4. **Shared Go code** → `packages/go-api-lib` | **Shared UI** → `packages/ui`
5. **`internal/` is private** — Go enforces this at compile time; respect it in spirit for TS too

## Conventions

- **Naming:** PascalCase React components, camelCase TS functions, kebab-case files
- **Imports:** use `@/` alias for within-app imports in Next.js apps
- **Go imports:** use full module path (`github.com/agency/<service>/internal/...`)
- **Commits:** conventional commits (`feat:`, `fix:`, `chore:`)
- **Branches:** `feat/desc`, `fix/desc`, `chore/desc`
- **PRs required** before merging to `main`
- **All env vars** must be documented in `.env.example` at root
